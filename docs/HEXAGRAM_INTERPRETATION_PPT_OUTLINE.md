# 卦象解释系统：从典籍证据到现代中文转述

> PPT 内容提纲
> 适用模块：Module 2A 起卦计算、Module 2B 交互解释、Module 3 典籍知识库

---

## 第 1 页｜项目目标

### 标题

卦象解释系统

### 副标题

以确定性计算和本地典籍证据约束 LLM 解释

### 核心目标

- 卦象由规则引擎计算，LLM 不参与起卦。
- 古籍原文、注释、译文来自 Module 3 本地知识库。
- LLM 只负责现代中文转述和谨慎的情境化说明。
- 所有传统解释均可通过证据 ID 和来源链接复核。

### 建议讲解

系统将“计算”“典籍证据”和“现代解释”分开处理。这样可以避免 LLM 自行生成卦象、伪造爻辞或编造古籍出处。

---

## 第 2 页｜模块职责

| 模块 | 主要职责 | 不负责的内容 |
| --- | --- | --- |
| Module 2A | 计算六爻、本卦、动爻、互卦和变卦 | 不生成古籍原文，不作自由解释 |
| Module 3 | 保存和检索卦辞、爻辞、注释、译文及来源 | 不重新起卦，不修改计算结果 |
| Module 2B | 整理用户问题、选择解释证据、调用 LLM、展示结果 | 不修改卦象，不允许 LLM 选择或补写典籍 |

### 系统边界

```text
谁产生数据：Module 2A
谁提供证据：Module 3
谁组织表达：Module 2B
```

---

## 第 3 页｜完整解释流程

```mermaid
flowchart LR
    A[用户问题] --> B[Chatbot 补充必要信息]
    B --> C[Module 2A 规则引擎]
    C --> D[本卦、动爻、互卦、变卦]
    D --> E[固定变爻选择规则]
    E --> F[Module 3 本地知识库]
    F --> G[Evidence Pack]
    G --> H[受约束的 LLM]
    H --> I[现代中文转述]
    I --> J[引用校验与分层展示]
```

### 处理原则

1. 规则引擎先完成全部卦象计算。
2. 系统根据动爻数量决定需要哪些典籍文本。
3. 后端从本地知识库精确提取证据。
4. LLM 只能阅读本次 Evidence Pack。
5. 服务端检查 LLM 使用的每个证据 ID。
6. 页面分别展示原文、传统注释、译文、现代转述和来源。

---

## 第 4 页｜固定变爻选择规则

| 动爻数 | 系统选择的典籍证据 |
| ---: | --- |
| 0 | 本卦卦辞 |
| 1 | 本卦对应动爻的爻辞 |
| 2 | 本卦两条动爻爻辞，以上爻为主要证据 |
| 3 | 本卦卦辞和变卦卦辞 |
| 4 | 变卦两条静爻爻辞，以下爻为主要证据 |
| 5 | 变卦唯一静爻的爻辞 |
| 6 | 乾、坤使用“用九”或“用六”；其他卦使用变卦卦辞 |

### 为什么固定规则

- 相同卦象总会选择相同类型的证据。
- LLM 无权挑选更符合某种结论的爻辞。
- 解释过程可以通过规则版本 `changing-lines-v1` 复现。
- 规则和典籍内容分别维护，避免重复建立古籍数据库。

## 第 5 页｜Module 3 典籍数据

### 当前覆盖范围

| 数据 | 覆盖情况 |
| --- | ---: |
| 六十四卦卦辞 | 64 / 64 |
| 六爻爻辞 | 384 / 384 |
| 乾卦用九 | 已收录 |
| 坤卦用六 | 已收录 |

### 数据字段

```text
original       古籍原文
commentary     传统注释，例如《彖传》《象传》
translation_en 资料来源所附英文译文
source_id      稳定的来源标识
title          书名和卦名
edition        来源平台或版本
chapter        卦序或章节
url            可访问的原始来源链接
```

### 精确查询接口

```http
GET /api/knowledge/hexagram?number=49&line=3
```

接口按卦序和爻位取证，不依赖模糊关键词，也不在资料缺失时生成替代原文。

## 第 6 页｜Evidence Pack

Evidence Pack 是一次解释允许使用的完整证据白名单。

```json
{
  "rule_version": "changing-lines-v1",
  "selection_rule": "1 动爻：采用本卦该动爻爻辞。",
  "question": "未来三个月是否适合调整工作？",
  "primary": { "number": 49, "name": "泽火革" },
  "transformed": { "number": 17, "name": "泽雷随" },
  "moving_lines": [3],
  "evidence": [
    {
      "evidence_id": "hexagram-49-line-3",
      "role": "primary_moving_line",
      "original": "九三：征凶，贞厉。革言三就，有孚。",
      "commentary": ["传统注释内容"],
      "translation_en": "Source-provided translation",
      "source_ids": ["ctext-zhouyi-49"]
    }
  ]
}
```

### Evidence Pack 的作用

- 缩小 LLM 可使用的资料范围。
- 记录本次解释为何选择这些文本。
- 将每一段解释连接到具体证据和来源。
- 支持后续复盘、测试和审计。

---

## 第 7 页｜LLM 的职责与限制

### LLM 可以做什么

- 将古文和传统注释转述为清楚的现代中文。
- 根据用户问题给出条件化的理解角度。
- 明确指出证据不足或无法判断的部分。

### LLM 不可以做什么

- 计算或修改本卦、动爻、互卦和变卦。
- 补写 Evidence Pack 中没有的卦辞、爻辞或注释。
- 编造书名、人物、年代、出处和链接。
- 给出古籍没有支持的具体日期、概率或必然结果。
- 把现代建议描述成古籍原意。

### 输出合同

```json
{
  "readings": [
    {
      "evidence_id": "hexagram-49-line-3",
      "modern_chinese": "现代中文转述"
    }
  ],
  "contextual_reflections": [
    {
      "text": "结合用户问题的谨慎说明",
      "evidence_ids": ["hexagram-49-line-3"]
    }
  ],
  "uncertainties": ["现有资料不能支持的判断"]
}
```

生成参数使用低随机性设置，当前温度为 `0`。

## 第 8 页｜页面展示

页面按照证据层级展示，不把所有内容混成一段回答。

| 展示层 | 内容 | 是否允许 LLM 修改 |
| --- | --- | --- |
| 计算结果 | 本卦、动爻、互卦、变卦 | 不允许 |
| 典籍原文 | 卦辞、爻辞、用九或用六 | 不允许 |
| 传统注释 | Module 3 收录的注释 | 不允许 |
| 资料译文 | 来源资料附带的译文 | 不允许 |
| 现代转述 | 对原文和注释的现代中文说明 | 允许，但必须引用证据 ID |
| 情境反思 | 联系用户问题的条件化说明 | 允许，但必须引用证据 ID |
| 来源 | 书名、版本、章节、URL | 不允许 |

### 降级处理

- LLM 未配置或调用失败：仍显示本地典籍证据。
- LLM 返回非法证据 ID：拒绝该输出。
- Module 3 缺少必要资料：提示资料缺失，不生成替代古文。

## 第 9 页｜如何检验解释是否正确

### 第一层：数据完整性

- 检查 64 卦和 384 条爻辞是否完整。
- 检查乾卦用九和坤卦用六是否存在。
- 检查卦序、卦名、爻位和原文的对应关系。

### 第二层：引用有效性

- 每个 `evidence_id` 必须存在于本次 Evidence Pack。
- 每个 `source_id` 必须存在于 Module 3 数据库。
- 页面引用的书名、章节和 URL 必须来自服务端返回值。
- 原文引用必须与数据库内容逐字一致。

### 第三层：语义忠实度

对每段现代转述检查：

1. 核心意思是否来自原文或传统注释。
2. 是否将“可能、谨慎、等待”等含义改写成必然结论。
3. 是否新增原文没有的具体时间、概率、人物或事件。
4. 是否把现代建议错误地归为古籍结论。
5. 是否清楚说明证据无法支持的部分。

### 第四层：稳定性

- 对同一个 Evidence Pack 重复生成 5 至 10 次。
- 比较核心含义、引用 ID 和结论边界是否一致。
- 用无关问题或提示注入测试，确认模型不会绕过 Evidence Pack。

## 第 10 页｜测试与验收

### 自动测试

当前测试覆盖：

- 0 至 6 个动爻的证据选择规则。
- 两动爻的上爻优先顺序。
- 四动爻的下静爻优先顺序。
- 乾卦用九和坤卦用六。
- 64 卦与 384 条爻辞的数据完整性。
- 非法证据 ID、非法 JSON 和资料缺失时的拒绝或降级逻辑。

### 人工黄金测试集

建议建立至少 20 个固定案例，覆盖不同动爻数量和问题类型。每个案例预先定义：

- 必须使用的典籍证据。
- 允许表达的核心含义。
- 不允许生成的推断。
- 可接受的资料边界说明。

### 评分表

| 指标 | 分值 |
| --- | ---: |
| 原文忠实度 | 0–2 |
| 注释一致性 | 0–2 |
| 引用准确性 | 0–2 |
| 无依据扩写控制 | 0–2 |
| 现代中文清晰度 | 0–2 |

建议将 8 分设为最低验收标准；引用错误或伪造典籍直接判定不合格。

---

## 总结页可用表述

卦象解释采用“规则选证据、数据库提供原文、LLM 负责转述、服务端验证引用”的架构。计算结果和古籍内容始终由确定性系统控制。LLM 只在证据范围内生成现代中文说明，并通过自动测试、来源核验和人工黄金案例检查解释质量。
