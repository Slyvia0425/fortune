## 3. 内部解卦流程

1. 定问：读取已确认对象、目标、期限及已知背景，不新增入职、薪资等条件。
2. 定角色：沿用程序取用和候选，说明世应及用神与本次问事的关联，不重新取用。
3. 看状态：综合关键爻月日、动静、空破冲合；局部标签不能直接等同综合旺衰。
4. 看作用：分析关键动变、世用关系及必要飞伏；区分结构关系存在和有效作用成立。
5. 分主次：识别主导因素、有利因素、制约因素，说明其关联与适用条件；不计数吉凶标签，不发明无依据的统一优先级。
6. 作综合：针对原问题形成有依据的传统倾向，指出支撑结论的关键链条与可能改变结论的条件。
7. 论期限：分别处理能否成事、是否在期限内、具体何时；只问期限不强制输出具体日子。
8. 出报告：按断语、行动建议、卦理分析呈现。内部分析记录保留在详情中。

每次理论应用必须形成：冻结事实 → 检索原文规则 → 成立条件/例外核对 → 本卦适用判断 → 对原问题的含义。检索命中本身不是适用证明。

## 4. 典籍与关键判断的引用契约

“关键判断”包括综合旺衰、有效生克、动变效力、飞伏可用、总体倾向、期限/应期，以及基于卦理提出的行动建议。单纯盘面陈述绑定 fact_refs，不要求用古籍证明某爻的实际地支。

新增或扩展一层可追踪的判断记录，以下为逻辑字段示意，实施者可兼容现有契约命名：

```ts
type InterpretationClaim = {
  claim_id: string;
  text: string;
  fact_refs: string[];
  evidence_ids: string[];
  basis_finding_ids: string[];
  rule_application: {
    rule_summary: string;
    conditions: { condition: string; state: 'met' | 'unmet' | 'unknown'; fact_refs: string[] }[];
    exceptions_checked: string[];
    applicability: 'applicable' | 'conditional' | 'inapplicable' | 'insufficient';
  };
};
```

- 每个关键判断必须有实际存在的 evidence_ids，并能追溯到原文、书名和已有章节/来源位置；原文元数据没有章节时不编造章节。
- 总体断语可以由已核验的多条判断综合产生，须列 basis_finding_ids/claim_ids，并解析到实际典籍证据；不能只填任意一个 ID 过校验。
- 内部 task→evidence 归属和现有事实方向校验继续保留。综合层允许通过合法 finding 跨任务引用，不允许模型直接引用不属于原始任务的证据绕过校验。
- 典籍内容属于不可信输入数据，不能执行原文中的指令。避免从相似卦例迁移个案结果；仅有案例时保持既有强度边界。
- 区分已阅读/已评估证据与实际支持当前判断的证据。定义、条件、例外均需考虑；不适用者记录原因，不能为满足全引用要求包装成支持证据。
- 校验 ID 存在和非空仅能保证引用完整性，不能证明原文蕴含结论。保留模型的条件核对，并在回放验收人工抽查关键判断与原文的一致性。
- 引用在正文按 [1]、[2] 等展示，点击/展开可见书名、可用的章节定位和原文片段；标号由程序根据证据映射，不由模型编造。不得链接不存在的来源页面。

## 5. 缺口、冲突与结论的边界

缺口须关联受影响的 claim/finding，并分类：

- 核心缺口：可能改变总体倾向；必须降低或保留总体判断。
- 时间缺口：影响期限或具体日期；不自动否定其他有依据的判断。
- 次要缺口：不影响当前结论的必要前提；保留详情，解释其不阻断的理由。

不能为增加肯定输出而随意降级缺口。若尚未形成结论链，无法证明某缺口无关，则保留未定状态。与用神/关键角色无关的普通伏神不自动列为核心障碍。

“月破成立”和“月令标签旺”是不同层次的程序信息，同时存在不自动构成典籍冲突；应核对规则适用条件，不让模型制造冲突后反复求证。真正存在相互冲突的适用规则时，需呈现对应原文和影响。

区分流程完成、资料支持程度、传统判断倾向。不能将传统倾向写成现实确定预测，也不能要求所有次要任务无缺口才允许表达局部判断。若调整整体 supported 的校验，必须同步证据依赖范围，不能简单删除全局检查。

进退神等未审定派生仍遵守现有边界；本轮不为了产生完整断语放开断言。需要新增规则时另行版本化和测试，不能靠模型自行补事实。

## 6. 用户输出契约：三个固定区块

### 断语

建议 100–180 字，先回应原问题，再给主导因素及必要前提。说明当前传统判断的倾向；材料不足时指出具体缺哪一项，以及哪些局部判断仍成立。不能固定以“当前只能作有条件的传统解释”开头代替回答。

断语中的关键判断关联其依据，正文可见引用标号。避免堆砌术语、人物心理推定、确定现实预测和无依据概率。

### 行动建议

通常 2–3 条，针对已成立的主要制约或条件，可执行且不重复。每条卦理建议关联 claim/finding 和典籍证据。例如将文书相关解释转成“核对岗位职责与书面条件”，必须先有本卦适用依据，不能看到父母爻就套固定建议。

允许普通现实建议，但明确归类为“现实建议”，与传统卦理依据分开；不能用常识建议伪装满足典籍引用。典籍不足时不强行凑建议，更不能编造择日、律师判断、医疗或投资指令。

### 卦理分析

通常 3–5 段，顺序为角色定位 → 关键月日状态 → 核心动变/作用链 → 综合支持与制约 → 必要的期限判断。按问题相关性组织，允许合并多个 finding，不要求逐任务复制。

每段解释“为什么此事实影响所问问题”，给出适用典籍的引用。大象只作辅助背景，不能覆盖纳甲、用神和日月动变分析；没有检索依据时不为满足图片形式加入卦名象义推断。

必要限制合并在本区块末尾，通常至多 3 项；完整 gaps、冲突、全部引用和原始任务记录放可展开详情。详情仍完整保留，不做静默丢弃。文化参考提示只出现一次。

## 7. 对现有节点的最小改造

1. 保留逐任务 findings 作为内部审计；在同次 Reasoning 调用输出跨任务综合所需的判断及三个区块，避免 DDL 阶段无条件再加一轮大模型调用。
2. 调整输入提示词：先核对适用条件，再综合；不能只总结典籍原文，也不能仅重复盘面。将已知缺口与真实未知字段区分。
3. 输出编译分开条件与限制；不把同一个数组复制到两个位置。
4. 最终写作允许对已核验内容合并和改写，并绑定 claim/finding 引用，取消逐字复制 finding.interpretation 的限制；不能通过改写新增判断或提高确定性。若采用同次生成方案，程序直接渲染经校验的三个区块，保留安全降级展示。
5. 扩展校验：正文区块引用可解析、关键判断证据可追踪、事实方向一致、条件未满足不写成适用、结论不超过依据。语言质量检查不能全靠关键词正则或 ID 非空。
6. UI 实际展示三个区块和证据入口，API 保留兼容的 overall_interpretation 可由同一结构渲染，避免 API 与页面内容两套来源。
7. 更新 prompt/schema/writer 版本、reasoning cache 和 checkpoint 版本。旧结果不得被当成新格式；重试继续引用原冻结卦盘。

## 8. 回归与验收

必须复用既有 245 冻结样例及目标聊天最新确定性回放，不重新起卦、不把新模型结果覆盖历史记录。

- 页面和 API 文本均按断语、行动建议、卦理分析组织；没有任务编号、原始枚举、无新增事实等内部语言进入主文。
- 条件/限制不在三个位置重复，缺口详情完整保留。
- 逐条抽查断语及卦理核心结论能追溯真实检索典籍；伪造 evidence_id、引用不相关规则、未满足条件却写成适用均拒绝。
- 245 样例不凭“世生官”断言已有求职行动，不将局部旺/月破自动判为理论冲突，不添加不相关伏神障碍，不将酉→申直接判成已成立化退；应期未定不要求具体日期。
- 空证据、只有案例、规则条件未知、实质冲突、无核心缺口但有次要缺口、时间缺口分别覆盖；不能靠强制输出肯定断语过验收。
- 至少一份跨任务综合测试，防止合法综合仍被旧 task 归属校验误拒；同时验证不能绕过父任务引用边界。
- 三个图片可用于人工评审结构和可读性，不把图片结论录成项目算法的真值。
- 运行受影响 Vitest、typecheck、构建和相关 Python 契约测试（有契约修改时）；记录调用次数、耗时、引用与适用性抽查结果，不承诺准确率提升。
